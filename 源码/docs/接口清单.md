# 接口清单

约定：
- 统一前缀 `/api`，前端通过 Vite 代理到 `http://localhost:8080`
- 统一返回体 `{ code, msg, data }`，`code = 0` 成功，`400` 业务/参数错误，`401` 未登录，`403` 无权限
- 登录态基于 Session（Cookie `JSESSIONID`），除登录注册外所有接口都经过 `LoginInterceptor`
- `familyId` 由服务端从 Session 取，**不接受前端传参**
- 统计类接口的区间参数统一支持三种写法，优先级从高到低：
  `startDate + endDate` > `year + month` > 只传 `year`；都不传默认当年

## 权限模型

三个角色（`t_user.role`，常量见 `com.gjp.common.Role`）：

| role | 角色 | 数据可见范围 | 可管理 |
| ---- | ---- | ------------ | ------ |
| 0 | 普通成员 | **只能看自己名下**的流水、统计、分析、查重、日志 | 只能录/改自己的流水 |
| 1 | 户主 | 本家庭全部成员，可切换查看任意成员 | 成员、成员账号、分类、资产负债 |
| 2 | 系统管理员 | 不属于任何家庭，看不到任何账单金额 | 网站维护、跨家庭日志、账号启禁用与重置密码 |

收敛点集中在 `UserContext`：

- `scopeMemberId()` 返回 `null`（可看全家）或成员ID（只能看这个成员）；管理员调用直接 403
- `resolveMemberId(前端传的)` —— 普通成员传什么都会被强制成自己，**改请求参数无法越权**
- `requireOwner()` / `requireAdmin()` / `requireFamilyMember()` —— 三道守卫

注意 `isOwner()` 是 `role == 1` 的**严格相等**而非 `>= 1`：
系统管理员 `family_id = 0`、不绑定成员，若让它通过户主校验，
它就能往「0 号家庭」里写业务数据，是一个真实的越权口子。

所有统计、分析、查重接口都额外支持 `memberId` 参数：户主用它切换查看对象，普通成员传了无效。

## 三、收支分类 `/api/category`（乙）

分类为**三级**结构（需求第 2 条）：`文化娱乐(1级) → 影音娱乐(2级) → 游戏充值 / KTV(3级)`。
`t_category` 冗余了 `level` 与 `root_id`（所属一级分类ID），
统计按一级汇总时只需一次等值 JOIN，不必连续 JOIN 两次父表。

| 方法   | 路径     | 参数                                            | 说明                                     |
| ------ | -------- | ----------------------------------------------- | ---------------------------------------- |
| GET    | `/list`  | `type?`（1=收入 2=支出）                        | 平铺列表，带 `level` / `parentName`      |
| GET    | `/tree`  | `type?`                                         | 三级树，供级联选择器用；一次查询内存建树 |
| POST   | ` `      | `categoryName, parentId, type, sortNo?`         | 最多三级；子分类类型必须与父一致；**仅户主** |
| PUT    | `/{id}`  | `categoryName, sortNo?`                         | 只允许改名与排序，类型和父级不可改；**仅户主** |
| DELETE | `/{id}`  | —                                               | 预置分类、有子分类、被流水引用时均拒绝；**仅户主** |

## 四、收支流水 `/api/record`（丙）★核心

| 方法   | 路径       | 参数                    | 说明                                             |
| ------ | ---------- | ----------------------- | ------------------------------------------------ |
| POST   | `/page`    | `RecordQuery`（见下）   | 返回 `{ page: {total, list}, sumIncome, sumExpense }`，合计按全部匹配记录算 |
| GET    | `/{id}`    | —                       | 详情                                             |
| POST   | ` `        | 流水字段                | 录入                                             |
| PUT    | `/{id}`    | 流水字段                | 编辑                                             |
| DELETE | `/{id}`    | —                       | 删除                                             |
| DELETE | `/batch`   | `[id, id, ...]`         | 批量删除，一次最多 200 条；查重页勾选后调用      |
| GET    | `/options` | —                       | 历史商家、历史片区、支付方式候选，供录入页联想   |

列表返回的每条流水额外带三个非数据库字段，供前端拼分类路径：
`parentCategoryName`（直接父级）、`rootCategoryName`（所属一级）、`categoryLevel`（1/2/3）。
三级分类显示为「餐饮支出 / 外出就餐 / 快餐」，只有父级时显示两段。

`RecordQuery` 字段（全部可空，为空即不参与过滤）：

```
type          1=收入 2=支出
memberId      成员
categoryId    分类；传一级分类时自动含其下全部二级分类
startDate     起始日期（含）
endDate       结束日期（含）
keyword       模糊匹配商家与备注
payMethod     支付方式
area          消费片区
isGift        1=人情往来 0=非
minAmount     金额下限
maxAmount     金额上限
pageNum       页码，从 1 开始，默认 1
pageSize      每页条数，默认 10，上限 200
```

流水字段：`type, memberId, categoryId, amount, recordDate, merchant, area, payMethod, isGift, remark`

服务端校验（`RecordService.validate`）：

- 成员、分类必须属于当前家庭
- 分类的收入/支出类型必须与流水类型一致（防止「工资收入」被记成一笔支出）
- 金额 > 0 且 ≤ 99999999.99，统一保留两位小数
- 发生日期不得晚于今天、不得早于 2000-01-01
- 支付方式只能是 现金/微信/支付宝/银行卡/其他
- 备注不超过 255 字

## 六、智能分析 `/api/analysis`（丁）★评分点

| 方法 | 路径      | 参数 | 说明                                     |
| ---- | --------- | ---- | ---------------------------------------- |
| GET  | `/report` | 区间 | 返回按严重程度排序的分析结论列表         |

每条结论结构：`{ code, level, title, basis, suggestion }`，
`level` 取 `danger / warning / info / good`。

分析规则：

| 编号 | 规则             | 判定逻辑                                                     |
| ---- | ---------------- | ------------------------------------------------------------ |
| A1   | 异常月份归因     | 支出最高月 vs 其余月平均，超 30% 判异常；再钻取到一级分类找出超支主因，并根据该分类在其他月份的水平判断偶发/持续 |
| A2   | 环比分析         | 最近两个有数据月份支出涨跌超 ±20%                            |
| A3   | 结余健康度       | 结余率 =（收入−支出）/收入；为负判入不敷出，< 10% 判储蓄空间不足 |
| A4   | 成员预算预警     | 使用率 > 100% 判超支，≥ 80% 判接近上限                       |
| A5   | 支出结构集中度   | 占比最高的一级分类 > 50% 判结构单一                          |
| A6   | 商家消费集中度   | 单一商家占已填写商家消费 ≥ 20%                               |
| A7   | 片区消费分布     | 单一片区占比 ≥ 40%                                           |
| A8   | 人情往来专项     | 人情往来支出占总支出 ≥ 10%                                   |

阈值定义在 `AnalysisService` 的常量中，可按家庭实际情况调整。

## 八、账单查重 `/api/dedup`（需求第 6 条）

| 方法   | 路径       | 参数                                                              | 说明                     |
| ------ | ---------- | ----------------------------------------------------------------- | ------------------------ |
| GET    | `/scan`    | `dayTolerance?`(默认3) `sameMember?`(默认true) `sameCategory?`(默认false) `startDate? endDate? memberId?` | 扫描疑似重复，返回分组 |
| DELETE | `/records` | `[id, id, ...]`                                                   | 用户勾选后删除           |

返回结构：

```
{
  groups: [{
    amount, count, maxDayDiff,
    matchType,      // 完全一致 / 高度相似
    reason,         // 判定理由，前端直接显示
    suggestKeepId,  // 建议保留的流水ID（组内最早录入的）
    records: [...]  // 组内全部流水明细
  }],
  groupCount, extraCount, extraAmount, truncated
}
```

实现要点：

1. **SQL 只找两两配对**，靠 `a.amount = b.amount` 等值条件把候选集压到很小，
   再用 `a.id < b.id` 去掉重复配对和自身配对，`ABS(DATEDIFF(...)) <= 容差` 覆盖"时间相近"。
2. **应用层用并查集合并成组**。若 A-B 重复、B-C 重复，配对表里是两条记录，
   直接按配对展示会让用户看到两组、同一条流水出现在多组里，勾选删除极易删错；
   合并成 `{A,B,C}` 一组才符合直觉。
3. **不提供自动删除**。金额时间相同完全可能是两笔真实消费（同一天买了两杯一样的咖啡），
   系统只挑出可疑项并说明理由，删哪条由用户决定 —— 即需求里"把删除权交给用户"。

## 九、操作日志 `/api/log`（需求第 7 条）

| 方法 | 路径           | 参数        | 说明                                   |
| ---- | -------------- | ----------- | -------------------------------------- |
| POST | `/page`        | `LogQuery`  | 分页查询，范围按角色自动收敛           |
| GET  | `/module-stat` | —           | 按模块的条数分布                       |
| GET  | `/options`     | —           | 模块与动作的可选值，前端下拉框用       |

`LogQuery`：`familyId?`(仅管理员有效) `userId?` `module?` `action?` `success?` `keyword?`
`startTime? endTime?` `pageNum pageSize`

管理员调用 `/page` 时只返回 `familyId / module / action / success / createTime`，
不返回 `username / realName / summary / detail / ip / errorMsg`，避免把账单金额、
消费内容或操作人信息带到系统维护界面。

设计取舍：

- **只记写操作**（新增/修改/删除/批量删除/导入/登录/退出/重置密码/启禁用），不记查询。
  查询量是写操作的几十倍，全记会让日志表迅速变成库里最大的表，而对排查问题几乎没有帮助。
- `detail` 存 JSON 文本而不拆成多列 —— 各模块要记的字段差别很大
  （流水记金额和分类，导入记文件名和成功条数），拆列会出现大量空字段。
- **写日志失败绝不影响主业务**：`OperationLogService.save()` 吞掉所有异常，
  只打一条 error 日志，不能因为日志表写不进去而让用户的记账操作回滚。
- `family_id = 0` 表示与家庭无关的系统级操作（如管理员登录）。

## 十一、文件导入 `/api/import`（第二批需求 1）

智能体只抽出结构化 JSON，**不写 MySQL**。表格优先直连通义，失败再走本地 Dify。入库仍走 `RecordService.addImported`，家庭隔离与金额/日期/分类校验与手工记账相同。

| 方法 | 路径 | 参数 | 说明 |
| ---- | ---- | ---- | ---- |
| GET | `/config` | — | `{ configured, mode, maxFiles, accept }`，**不回传 API Key** |
| POST | `/jobs` | multipart `files` + `memberId?` | 落盘、建任务、入队，立刻返回 job；一次最多 10 个，单文件 12MB，整次不超过 120MB |
| GET | `/jobs` | — | 当前用户可见的最近 20 个任务（含文件进度，不含流水明细） |
| GET | `/jobs/{id}` | — | 任务 + 文件进度 + 待确认流水；解析中前端 1 秒轮询 |
| POST | `/jobs/{id}/cancel` | — | 取消排队/解析中的任务；已抽出的待确认流水仍保留 |
| POST | `/jobs/{id}/files/{fileId}/cancel` | — | 取消还在排队或正在解析的单个文件 |
| POST | `/jobs/{id}/confirm` | `{ itemIds?, merge? }` | 把 pending 项确认入库；`merge=true` 时同一天同金额同商家只留一份；省略 itemIds 表示全部 pending |

任务状态：`queued` → `running` → `preview` → `importing` → `done`；整单失败为 `failed`，用户停止为 `cancelled`。
文件状态：`queued` / `parsing` / `ready` / `rejected`（无关账单） / `failed` / `cancelled`。
不同用户最多同时跑 3 个解析任务，互不排队；刷新页面不会中断后台解析。

权限：仅家庭成员。管理员 403。普通成员 `memberId` 强制自己；户主可代记。普通成员只能看自己发起的任务。

允许格式：jpg/jpeg/png/webp/bmp、xls/xlsx/csv、pdf。带表头的账单表、微信/支付宝证明 PDF 本机抽取；认不出的表才交给通义文本或 Dify。图片和扫描件整文件交给 Dify，由文档提取器或市场读文件工具抽文字，不在本机做 OCR。未配置 `DIFY_API_KEY` 时，带文字的 Excel/CSV/PDF 仍可用。

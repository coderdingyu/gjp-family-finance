# 智能分析 v2：本地事实、证据引用与渐进增强

## 本次变更

- 商家榜 SQL 使用 MySQL 8 窗口汇总计算全部合格商家的分母，LIMIT 只控制展示条数。
- 月均和分类归因使用同一组完整且有支出的月份；不足三个月不归因。环比不跨无记录月份，不完整的历史边界月份不参与。
- 记录覆盖情况明确区分未完整覆盖、无记录、已记支出为零。系统无法证明账目完整，不能把无记录自动当成真实零支出。
- 预算发现以 `A4:memberId:YYYY-MM` 唯一定位。同名成员不会合并，AI 也不会覆盖任何 A* 条目。
- 历史预算尚未版本化，明确显示“按当前预算参考”，不伪装成当时的执行率。
- 相邻月份增加分类的次数 / 单笔均额采用算术分解：次数效应 = (本期次数−上期次数) × 上期单笔均额；均额效应 = 分类金额差额−次数效应。不代表真实因果或商品涨价。
- 分类、商家和人情占比作为中性参考，不自动判定浪费。不自动排除重复账单、不自动修改预算或记录。

## API（前后端需一起更新）

`GET /api/analysis/report?startDate=2026-01-01&endDate=2026-08-31&memberId=...&refresh=false`

返回报告对象，不再返回旧版条目数组：`reportId/generatedAt/ruleVersion/startDate/endDate/memberId/scopeLabel/totals/quality/notices/items/aiConfigured/aiStatus/aiMessage/aiInsights`。
仅做本地分析，不调用 Dify。每次生成先在只读、可重复读事务内取得聚合快照。

`POST /api/analysis/enhance`，请求体 `{"reportId":"..."}`。

按当前用户、家庭、角色、绑定成员、会话版本和实际分析成员重新校验权限。
返回同一份本地事实及增强状态：`rules` / `enhanced` / `fallback`。空数据不调用 AI。
界面由用户按需点击增强，发送前显示数据说明：汇总事实可能包含名称和金额，发至配置的 Dify 服务，不发送流水原件。

报告只在内存保留三分钟、最多 64 份；缓存键包含有效权限范围、聚合事实指纹、规则及工作流协议版本、配置指纹。
再次生成会重新取数，聚合变化产生新报告；`refresh=true` 强制重新生成。同一快照的并发增强只调用一次。
证据入口查询的是当前流水，可能与快照之后修改过的账单不同，请关注生成时间。

## Dify 升级要求

重新导入并发布 `运行包/dify/管家婆智能分析.yml`。如果发布成新应用，需要更新本机 `DIFY_ANALYSIS_API_KEY`。
本地修改 YAML **不会**自动更新已部署的 Dify。未升级工作流时，旧格式会被拒绝并明确回退，不会显示伪造的“增强成功”。

输入仍为 `snapshot`、`rule_table`。输出改为：

```json
{"insights":[{"code":"S0","evidenceIds":["A4:2:2026-08"],"focus":"BUDGET"}]}
```

- 只允许 S0、S1、S2，必须含 S0；每条引用 1–3 个本报告的唯一 findingId。
- focus：GENERAL / CHANGE / BUDGET / INCOME / STRUCTURE，后端验证是否存在对应规则证据。
- 不接收自由文本、金额、姓名或覆盖 A* 的内容。后端从已引用事实和受控解释模板生成文案。
- 此处有意把 AI 限定为“选重点和解释方向”，不承诺自由文本已经过事实验证。

## 验证与部署边界

- Java 测试：在 `源码/server` 执行 `mvn test`。
- 前端纯逻辑测试：在 `源码/web` 执行 `node --test tests/analysis.test.mjs`。
- 前端构建：`npm ci && npm run build`；随后 `mvn package` 打出含新页面的 JAR。
- 本次不新增数据库迁移，不保存个人阈值、固定/一次性分类或历史报告。这些需要另行设计持久化和用户确认流程。
- 不直接覆盖交付目录旧 JAR、不重启当前网站。构建产物在 `源码/server/target`，部署前按原数据库升级流程备份核对。

# 云主机：按 dingyu 更新管家婆，并搭现行 Dify 工作流

适用：云上**已经在跑旧版管家婆**，要把本机 `dingyu` 的文件导入能力同步上去。

仓库：https://github.com/coderdingyu/gjp-family-finance  
**只拉 `dingyu`，不要 `git pull origin main`。`main` 还是旧提交。**

**不要**在云上重新执行 `运行包/schema.sql` 或 `data.sql`，那会丢掉现网家庭和流水。

本机抽得出的 Excel / CSV / 微信支付宝证明 PDF **不走 Dify**。  
只有本机认不出的怪表、图片小票、扫描件 PDF，才把**原文件**交给 Dify。

现行工作流（不要再搭经典 Agent）：

```
用户输入 → 文档提取 → 是否抽出文字
  → 有字：汇总 → 账单解析(LLM) → 结束(result)
  → 没字：PaddleOCR-VL-1.6 → 汇总 → LLM → 结束
```

详细安装步骤见同目录 [`导入说明.md`](./导入说明.md)。DSL：[`管家婆账单导入.yml`](./管家婆账单导入.yml)。  
不要导入、不要依赖 `管家婆读文件.yml`（旧工具，主流程已内联文档提取器）。

## 一、先更新管家婆（没有 Dify 也能用 Excel / 微信 PDF）

进入原来的交付包目录：

```bash
cd /path/to/管家婆-家庭收支管理系统-完整交付包
git fetch origin
git checkout dingyu
git pull origin dingyu
```

如果云上当初不是 git 部署，在本机拉 `dingyu` 后再把下面几个文件拷上去：

- `运行包/gjp-server-1.0.0.jar`（已带新前端）
- `运行包/patch_import.sql`
- `运行包/dify/`（说明、DSL、样例）

核对：`git rev-parse --abbrev-ref HEAD` 必须是 `dingyu`，不要停在 `main`。

### 1. 补三张导入表（没有才补）

按云上真实账号改用户名和库名：

```bash
mysql -u root -p gjp < 运行包/patch_import.sql
```

脚本是 `CREATE TABLE IF NOT EXISTS`，可重复执行。成功后应有：

- `t_import_job`
- `t_import_file`
- `t_import_item`

### 2. 换 jar 并重启

```bash
# 停掉旧进程（按你原来的方式，例如 systemd 或下面这行）
kill $(lsof -nP -iTCP:8080 -sTCP:LISTEN -t)

# 若你不是用 运行包 里的 jar 启动，先覆盖你实际在跑的那个文件
cp 运行包/gjp-server-1.0.0.jar /你原来的路径/gjp-server-1.0.0.jar

# 先不配 Dify 也可以先起来，验证菜单
java -jar 运行包/gjp-server-1.0.0.jar
```

若用 systemd，改 `ExecStart` 指向新 jar 后 `sudo systemctl restart gjp`。

浏览器强刷（或清缓存）打开网站，左侧应出现 **文件导入**。上传 `运行包/dify/示例账单.csv`，应抽出多笔待确认流水。微信 Excel / 交易明细证明 PDF 也应在数秒内完成本机抽取。

此时图片小票若提示未配置 Dify Key，先继续第二节；不要去配管家婆进程里的 `DASHSCOPE_API_KEY`。

## 二、在云主机上搭 Dify（图片 / 扫描件 / 本机认不出的文件）

管家婆和 Dify 建议**同一台机器**，管家婆用 `127.0.0.1` 调 Dify，Dify 不必对公网开放。

建议版本与本机一致：**Dify 1.15.0**。不要默认去拉 latest。云上 Nginx **改到 8088**，不要占 80（管家婆用 8080）。

1. 按 [`导入说明.md`](./导入说明.md) 第 1 节安装。克隆时指定分支：

   ```bash
   git clone --branch 1.15.0 https://github.com/langgenius/dify.git
   ```

2. 编辑 `dify/docker/.env`：

   ```bash
   EXPOSE_NGINX_PORT=8088
   EXPOSE_NGINX_SSL_PORT=8443
   FILES_URL=http://127.0.0.1:8088
   INTERNAL_FILES_URL=http://api:5001
   ```

   `FILES_URL` 必须是插件能访问到的完整地址。空着时 PaddleOCR 会报相对路径 / `FILES_URL` 错误，图片导入失败。  
   **改 `.env` 之后**不要只 `docker compose restart`（不会重读环境变量），要用：

   ```bash
   cd dify/docker
   docker compose up -d --force-recreate
   docker compose restart nginx
   ```

3. 打开 `http://<云主机>:8088/install` 建管理员（或走 SSH 隧道，不要把 8088 长期对公网开放）。
4. 设置 → 模型供应商：装通义千问，填云厂商 Key。LLM 节点模型名 `qwen3.8-max`，**temperature ≥ 0.6**。
5. 插件市场安装 **PaddleOCR**（`langgenius/paddleocr`）。工具授权里填星河社区访问令牌。令牌只放 Dify 凭据，不要写进仓库、DSL 或管家婆 yml。
6. 工作室 → **导入 DSL**：`运行包/dify/管家婆账单导入.yml`。若云上已有旧的「管家婆账单导入」，用同一应用覆盖导入，**不要新建应用**（新建会换 Key，管家婆里的旧 Key 会失效）。
7. 打开编排，必须是下面这条，**不是**「智能体节点 + 读账单文件工具」：

   `用户输入` → `文档提取` → `是否抽出文字` →（有字）`汇总文件文字` → `账单解析`（**LLM**）→ `结束`  
   没字则先走 `大模型文档解析`（PaddleOCR-VL-1.6，文件入参绑 `bill_file`）再汇总。

   经典 Agent 在 Dify 1.15 不能带必填 file 工具，会报 `file type parameter not supported in agent`。
8. 点右上角 **发布**。只保存不发布，管家婆调到的仍是旧图。
9. 「访问 API」创建密钥（`app-` 开头）。

安全建议：安全组只放行管家婆端口（如 8080）。Dify 的 8088 只给自己 SSH 隧道或仅本机访问。必须从外网进工作室时，再临时放行并尽快关掉。

## 三、让云上的管家婆连上 Dify

重启前加上环境变量（Key 不要写进仓库或 `application.yml`）：

```bash
export DIFY_BASE_URL=http://127.0.0.1:8088/v1
export DIFY_API_KEY=app-你的密钥
export DIFY_MODE=workflow
java -jar 运行包/gjp-server-1.0.0.jar
```

不要配 `DASHSCOPE_API_KEY`。图片和认不出的表一律走上面的 Dify 工作流。

systemd 示例（`/etc/systemd/system/gjp.service`）：

```ini
[Service]
Environment=DIFY_BASE_URL=http://127.0.0.1:8088/v1
Environment=DIFY_API_KEY=app-xxxxxxxx
Environment=DIFY_MODE=workflow
# 云上 MySQL 若有密码，与原来保持一致即可
WorkingDirectory=/path/to/运行包
ExecStart=/usr/bin/java -jar /path/to/运行包/gjp-server-1.0.0.jar
```

`application.yml` 里数据源默认是 `localhost:3306/gjp`、root 空密码。云上如果不是这样，继续用你原来改过的 yml 或启动参数，不要被 git pull 覆盖丢了密码。可以用：

```bash
java -jar 运行包/gjp-server-1.0.0.jar \
  --spring.datasource.url='jdbc:mysql://127.0.0.1:3306/gjp?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false' \
  --spring.datasource.username=root \
  --spring.datasource.password='你的密码'
```

上传目录默认是进程工作目录下的 `uploads/import`，确保该目录可写。

## 四、验收

1. 登录云上网站 → **文件导入**。
2. `运行包/dify/示例账单.csv`：本机抽取，出现待确认即可（不要为了对齐本机去点入库，除非业务上要入库）。
3. `运行包/dify/无关文件.csv`：标成无关，不入库。
4. 微信 Excel / 交易明细证明 PDF：数秒出结果，不应超时，不应走 Dify。
5. 一张小票照片：走文档提取（空）→ PaddleOCR → LLM，抽出金额和商家。不应再开 LLM 视觉节点。
6. 本机认不出的表（如 `运行包/测试样例/本机认不出-大写金额.csv`）：把原文件交给 Dify，不应再按 50 行切块只传 `text_content`。

## 五、常见问题

| 现象 | 处理 |
| --- | --- |
| 拉完还是旧功能 | 看是不是拉了 `main`。必须 `git checkout dingyu && git pull origin dingyu`，再确认进程读的是新 jar。 |
| 菜单没有「文件导入」 | jar 还是旧的，或浏览器缓存了旧前端。确认进程读的是新 jar，强刷。 |
| 上传后报缺表 | 没跑 `patch_import.sql`，或跑到了别的库。 |
| 图片失败「未配置 Dify」 | 进程环境里没有 `DIFY_API_KEY`，改完必须重启 Java。 |
| 图片失败 `FILES_URL` / 相对路径 | `dify/docker/.env` 补上 `FILES_URL`、`INTERNAL_FILES_URL` 后 **`up -d --force-recreate`**，再 `restart nginx`。 |
| `request timed out` | 工作流没发布、模型没配、或仍是经典 Agent。重导 `管家婆账单导入.yml` 并发布。 |
| 通义报 temperature | 「账单解析」LLM 节点温度改到 ≥ 0.6 后重新发布。 |
| `file type parameter not supported in agent` | 还在用经典 Agent 挂 file 工具。按第二节第 7 步改成提取器 + OCR + LLM。 |
| PaddleOCR 没字 / 授权失败 | 插件已装、令牌已填、节点文件绑 `bill_file`，然后重新发布。 |
| git pull 覆盖了云上改过的密码 | 用启动参数或单独的 `application-prod.yml` 覆盖，不要把真实密码提交到 GitHub。 |
